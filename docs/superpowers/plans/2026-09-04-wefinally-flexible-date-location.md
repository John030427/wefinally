# WeFinally 自由约会地点与 AI 澄清修复计划

状态：待实施。本文仅为计划，不代表代码已修复或已部署。

## 1. 目标与范围

用户自行决定去哪里、做什么。地点允许商圈、商场、公园、公共场馆或具体门店，不以是否包含“餐厅”“影城”“店”等字样作为提交门槛。

核心原则：地点可以宽泛，双方确认必须明确；AI 帮助沟通，不替用户做决定。

本计划覆盖：第一次约会表单、服务端方案校验、LangGraph 澄清、双方方案卡和旧会话兼容。

不包含：QA 重置故障修复、删除历史记录、生产测试入口关闭、地图搜索/订位/购票、自动收集位置、开放用户私聊。重置故障必须独立追踪，不能把删除记录作为本问题的修复。

## 2. 已确认问题

审查基线为发布工作树 `wefinally-release-20260904` 的 `4613372`。实施前重新核对最新提交，不从保存本文的历史实验分支直接发布。

现有链路：

1. `dateCoordinationPolicy.normalizeApplication()` 调用 `meetingPlanPolicy.venueResolution()`。
2. “大运中心”“椰子鸡”等被判断需要具体门店，并把 `activity_venue` 设为空。
3. `invitationCoordination.resolvePrimaryInvitationProposal()` 把清空后的偏好与仍有原始地点的方案做严格比较。

## 3. 产品要求与验收规则

### R1：自由地点

- 当用户填写“大运中心”“万象城”“大运中心四季椰林”时，系统应保留文字并允许作为邀请地点，不要求 POI ID、门店后缀或地图验证。
- 当输入仅为活动/菜品，例如“椰子鸡”时，系统应保留原输入并询问地点，不把它错误地当成已确定地点，也不显示“超出范围”。
- 当地点缺失时，系统应允许保存草稿，提示“想在哪里见面？商场、商圈或具体店名都可以”；发送邀请前需要一个用户明确认可的地点范围。
- 地点只做长度、空白字符和安全校验。不得以正则识别不出店名为理由拒绝。
- “公共约会地点”与“精确住址/单位等敏感个人地址”严格区分；后者不得作为普通 AI 转述内容。

### R2：活动独立

- 当用户先填“万象城”再选“吃饭”，或反过来填写时，系统应得到相同方案。
- 活动类别与补充描述分开，例如活动“吃饭”、描述“椰子鸡”，不能覆盖地点。
- 更改活动不应清空地点；更改地点不应清空活动、时间和预算。

### R3：非强制澄清

- 当地点较宽泛时，AI 可以建议补充，但不得阻止邀请，也不得反复要求具体门店。
- 当用户表示“就在万象城，到了再选店”时，系统应记录“门店到场后商量”，停止重复追问。
- 当模型无法判断地点是否具体时，应保留输入并采用中性提示，不编造门店、地址、营业情况或路线。
- 模型不可用时，表单仍能提交合法地点；以固定提示提供选择，不依赖模型放行。

### R4：区分会合地点与活动场地

- 当用户说“星巴克看电影”，AI 应询问“先在星巴克碰面，再去看电影吗？”；未知意图不能直接拒绝，也不能直接确认方案。
- 当用户确认先碰面再去影院，应分别显示会合地点和后续活动安排；未选影院时标注“影院待商量”。
- 待澄清内容可以进入草稿/邀请，但必须显式展示，不得伪装成完整且已经双方认可的安排。

### R5：双端最终确认

- 发送邀请前展示日期、具体时间、地点、活动、预算、付款方式、时长和未定事项；用户主动确认发送。
- 最终约会仍要求具体日期及 `HH:mm` 时间，不能用“晚上”替代“20:00”。
- 商圈/商场级地点可用于最终确认，不强制升级成门店。
- “到场后选店/影院”等未定事项必须出现在同一版本方案卡上，并由双方确认。只有双方均接受该版本后才生效。
- 修改日期、时间、地点、活动或其他共享条件，应生成新版本，旧确认不得自动沿用。
- 单纯说“对”“可以”只在明确、唯一的待回答问题上下文内解释；不能同时替用户同意所有未确认字段。

### R6：到场与通知

- 现场位置与穿搭是可选补充，不是表单必填，不要求预先知道商场入口或座位。
- “我在吧台旁”等信息必须经过用户确认的业务操作转达，AI 不转发整段私有对话。
- 消息状态区分已记录、已投递和已读；未获得读取证据不得宣称对方已看到。

## 4. 技术设计

### 4.1 统一地点表达

采用兼容性增量字段，不急于破坏现有 contract v2：

| 字段 | 语义 |
|---|---|
| `activity_venue` | 用户认可的约会地点文本，允许商圈/商场；非空输入不得因“非门店”清空 |
| `activity_detail` | 菜品或活动补充，如“椰子鸡” |
| `location_precision` | `area` / `venue` / `unspecified`，仅作说明，不作为门店准入门槛 |
| `venue_choice_mode` | `named_location` / `choose_on_arrival` / `discuss_before_meeting` |
| `meeting_location_text` | 明确需要“先碰面再去活动场地”时使用；普通单地点流程不强迫填两次 |
| `open_items` | 需要商量的事项及是否已被双方接受为未定事项 |
| `clarification` | 唯一待澄清问题、涉及字段和对应方案版本；不存供应商 conversation ID |

保留最少必要的用户地点文本，不新增完整原始聊天存档。AI 输出地点分类只是建议，用户明确选择优先。

### 4.2 统一规范化与校验

建立同一规范化函数供表单申请和主方案使用，不能一边把地点清空、一边保留后再比较。

- 地点文本只做安全清洗，不以场所后缀推断合法性。
- `canSendInvitation` 与 `canFinalizePlan` 分开：邀请可含明确标注的待商量事项；最终确认必须有具体时间、地点范围，并处理双方对未定事项的认可。
- 校验失败返回字段级错误，例如 `LOCATION_REQUIRED`、`START_TIME_REQUIRED`、`PLAN_VERSION_STALE`；沿用仓库现有等价公开错误码，避免重复语义。
- 邀请人与接受方均使用相同规范化与方案比较规则，不按性别区分。
- 业务事实、版本、权限和通知始终通过确定性服务落库；LangGraph 只能调用白名单工具。

### 4.3 LangGraph 对话路径

理解用户修改 → 保留未修改字段 → 判断是否需要澄清 → 展示修改预览 → 用户确认发送 → 持久化新版本与投递事件 → 对方收到差异及完整方案 → 对方确认或继续修改。

地点宽泛本身不进入阻塞澄清。只有缺失地点、语义歧义或安全问题需要澄清；已有“到场后商量”决定不得被循环追问。

### 4.4 页面调整范围

- 表单先显示“想在哪里见面”，提示“商圈、商场或具体店名都可以，例如万象城、大运中心四季椰林”。
- 随后填写活动及可选说明；不增加强制的门店选择器。
- 具体时间保持必填；提前会合位置和穿搭保持选填。
- 发送按钮前展示方案预览；聊天页保留最新方案卡及对方修改摘要。
- 宽泛地点显示轻提示，不用错误 toast；真正缺项在对应字段附近显示说明。

### 4.5 旧记录兼容

- 旧非空 `activity_venue` 原样保留，不重新按门店字典拒绝。
- 若旧记录 `activity_venue` 为空但 `area_hint` 有可信原地点，可只读派生展示“原地点建议”；不得未经用户确认自动改变双方已经确认的事实。
- `activity_detail=椰子鸡` 不能自动回填成具体地点。
- 新客户端对旧记录补充展示状态，不批量清库；已确认方案如需修订，走新版本流程。
- 后端先做增量兼容，确保旧客户端不会把“待商量”误显示成双方已确认；无法安全兼容的动作返回明确升级提示。

## 6. 测试步骤与预期

先用纯函数测试和模拟依赖验证，再使用两个真实测试账号；不以清空历史为测试前提。

| 场景 | 操作 | 预期 |
|---|---|---|
| 商圈 | 填大运中心、吃饭、具体日期与20:00 | 可发送，不强制门店，不报范围冲突 |
| 商场 | 填万象城、吃饭 | 地点原文保留，可选择到场后商量店铺 |
| 具体门店 | 填大运中心四季椰林 | 不要求名称包含“店/餐厅”，正常发送 |
| 纯菜品 | 地点栏填椰子鸡 | 保留输入，询问在哪里吃；草稿可保存 |
| 不补门店 | 回复就在万象城，到了再选店 | 不再反复询问，卡片明确说明 |
| 活动歧义 | 星巴克看电影 | 询问是否先碰面再去影院，不硬拒绝 |
| 接受未定事项 | 双方确认万象城碰面、到场选店 | 同版本双确认后生效，无虚构店名 |
| 单方未认可 | A选择到场选店，B要求先确定店 | 不宣称最终方案已达成，继续协调 |
| 时间不具体 | 只写周日晚上 | 询问具体几点，不把 evening 当时间 |
| 改期 | 已确认后提出改为周日晚8点 | 新版本预览，旧确认失效，对端看到差异 |
| 更换活动 | 吃饭改为散步 | 地点不清空，保留未修改条件 |
| 旧记录 | 旧area_hint有地点、activity_venue空 | 展示可恢复建议并让用户确认，不直写历史 |
| 并发 | 双方同时修改方案 | 返回最新版本/冲突提示，不覆盖对方变更 |
| 弱网 | 确认发送时断网后重试 | 幂等，不重复邀请，不丢草稿 |
| 模型故障 | 模型超时 | 仍可用表单提交合法方案，不报虚假成功 |
| 到场 | A说我在吧台旁并确认转达 | B会话看到该提示；状态不混淆已发送和已读 |

真机操作顺序：A填写并预览 → A发送 → B收到完整邀请 → B提出修改 → A会话看到差异 → 双方确认同一版本 → A发送现场提示 → B刷新/轮询收到。互换发起方重复一遍。

测试记录仅保存脱敏截图、版本号、request ID、是否通过及失败步骤，不记录账号凭据或完整私人聊天。

## 7. 完成标准与发布阻断

- 全新与旧会话均无需删记录即可使用宽泛地点。
- 方案和偏好使用同一规范化表示，没有清空地点后误判范围的路径。
- 用户明确选择“到场后商量”后不再被强迫补门店。
- 双方最终确认针对同一版本和同一份未定事项；AI 无权代为确认。
- 新增确定性自检、图测试和两台真机流程均通过；本地成功不能代替云端验收。
- 若仍出现地点丢失、重复追问、单方确认生效、对端收不到消息或公开 `SERVER_ERROR`，停止发布并保留证据。
- 回滚须保留新增数据字段与已确认事实，不通过删历史记录回避兼容问题。
