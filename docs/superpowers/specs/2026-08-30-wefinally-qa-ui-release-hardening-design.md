# WeFinally QA 与核心体验收口设计

日期：2026-08-30

状态：待用户书面复核后进入实施计划

目标分支：`codex/tab-icons-admin-chat-domain`

## 1. 目标

本轮将已完成但仍有边界缺口的真机 QA 重录与匹配结果揭晓能力收口为可重复验证的流程，同时降低注册页职业身份选择负担，并统一小程序底部“匹配 / 记录 / 我的”导航图标。

本轮只提交代码、测试和说明文档，不部署 CloudBase、不上传微信小程序、不绑定或修改生产域名、不写生产数据库。

## 2. 产品原则

- 认真婚恋，不引入滑动匹配、头像墙或用户私聊。
- 正式用户的历史配对去重规则保持不变。
- QA 能力只对显式 QA 账号开放，不能通过普通客户端参数自行提权。
- 重新录入资料不能删除订单、VIP、推广归属、审核状态或真实历史记录。
- 页面首屏三秒内说明当前状态和唯一主要操作。
- AI 继续作为辅助服务，不扩大模型数据库权限。

## 3. 范围

### 3.1 QA 重录与可重复配对

现有实现会写入固定 `qa_match_cohort`，但历史 `match_claim` 仍会永久排除同一对账号。新设计不删除或改写历史 claim，而是为每次成功完成重录写入新的 QA 轮次标识和时间边界。

匹配历史判定规则：

1. 非 QA 用户：只要存在历史 pair claim，继续拒绝重复匹配。
2. QA 用户：双方必须都满足显式 QA 权限、处于相同 QA cohort、均已完成当前轮次重录。
3. 只有当历史 pair claim 的创建时间早于双方 `qa_match_run_started_at` 中较晚的那个边界，且双方各自的轮次都晚于该 claim 时，才允许在新 QA 轮次重新配对。换言之，必须两个人都在旧 claim 之后完成重录；只重录一方不能绕过去重。
4. 新交付的 claim 必须记录双方本轮 QA 标识组成的 canonical run key，后续同一轮仍禁止重复匹配。
5. 任意权限、cohort 或轮次字段缺失时，按正式历史去重规则 fail-closed。

新增字段沿用 NoSQL 文档的渐进式兼容方式：

- `user.qa_match_run_id`
- `user.qa_match_run_started_at`
- `match_claim.qa_match_run_key`

`qa_match_run_id` 由服务端在每个账号完成重录时独立生成，客户端不能指定。`qa_match_run_key` 由双方 user id 与双方 run id 按 canonical 顺序组合后计算，不作为权限凭证。为了保持两台真机操作简单，沿用当前受控 QA cohort；本轮不新增用户输入的配对码。测试操作规范要求同一 cohort 同一时间只放入待验证的一组可通过硬门槛的账号，其他负例必须被硬门槛排除。

### 3.2 注册页“其他符合身份”选择器

当前注册页一次展示最多 40 个标签，改为：

- 主表单只显示已选择的最多两个身份。
- 未选择时显示一个 88rpx 高的“选择其他身份”入口。
- 点击后打开底部抽屉。
- 抽屉包含搜索框、已选区和按 `plate_name` 分组的候选列表。
- 搜索匹配职业名称和板块名称；无结果时显示明确空态。
- 选择达到两个后，未选项保持可见但点击时给出限制提示。
- 主要身份不出现在补充身份候选中。
- 保存接口仍使用现有 `secondary_circle_ids`，不改变后端正式合同。

### 3.3 自定义底部导航

将原生无图标 tabBar 改为微信自定义 tabBar，保留三个既有页面与顺序：

1. 匹配：相遇/双向连接语义。
2. 记录：时间线/记录语义。
3. 我的：人物轮廓语义。

图标使用同一套圆角线性 mask data URI，不使用 emoji，不使用 WXML SVG 标签，不增加网络图片依赖。选中态使用 `#E8637F`，默认态使用 `#B5A5A5`。触控高度不低于 88rpx，并处理底部安全区。

每个 tab 页面在 `onShow` 同步选中索引；自定义 tabBar 只负责导航和视觉，不承载业务状态。

### 3.4 匹配结果揭晓

保留现有底部揭晓面板和日期判断，调整已看语义：

- 点击“立即查看”后记录该 `match_id` 已看，并进入详情。
- 点击“稍后再看”只在当前小程序会话内收起，不写永久已看记录。
- 同一会话内不重复打扰；下一次冷启动仍可再次展示。
- 本地存储失败不能阻止进入匹配详情。
- 未来如需跨设备同步，另建服务端 receipt，不在本轮扩大数据模型。

视觉继续使用轻奢柔粉：暖白面板、玫瑰粉单一主 CTA、克制呼吸光环。动效不展示虚构“AI 已匹配”过程，只表达已有结果抵达。

### 3.5 后台对话与域名边界

本轮只做代码侧和文档侧核对：

- 确认 Admin Web 已有会话列表、详情时间线和客服回复入口。
- 若现有导航入口不明显，只调整后台页面的信息架构与入口文案，不扩大角色权限。
- customer_service 只能读取允许的脱敏会话投影，不能读取 OpenID、手机号、另一方私密协调输入或原始模型 prompt。
- 提供短域名绑定所需的配置清单，但不购买域名、不修改 DNS、不上传证书、不部署静态站点。

## 4. 数据流

### 4.1 QA 重录

```text
QA 用户确认重录
→ 服务端复核 QA 权限
→ 事务内重置当前匹配设置并写 pending
→ 用户重新提交注册资料
→ 服务端完成资料更新并写新的 QA run 边界
→ 正式匹配读取双方 run 与历史 claim
→ 仅忽略早于当前双方 run 的旧 QA claim
→ 新 claim 写入本轮 run id
```

### 4.2 身份选择

```text
circle API
→ register 页面按 plate 分组
→ 主页面展示已选摘要
→ 底部抽屉搜索/选择
→ secondary_circle_ids
→ 沿用现有注册或资料更新接口
```

### 4.3 揭晓状态

```text
首页读取 latest match
→ 日期已到且未永久看过
→ 当前会话未 dismiss
→ 展示揭晓面板
   ├─ 立即查看：best-effort 写本地已看 → 详情
   └─ 稍后再看：仅内存 dismiss
```

## 5. 错误处理与安全

- QA 权限、cohort、run 任一不明确时，不绕过历史配对。
- 事务失败时不能留下“设置已清空但用户未进入重录”的半状态。
- 身份标签写入失败必须返回可诊断错误或保持既有数据，不能静默形成用户资料与标签不一致。
- 搜索和选择器只处理服务端返回的职业字典，不接受任意 HTML。
- tabBar 路由固定在本地白名单。
- 本地 storage 异常只影响已看持久化，不影响核心导航。
- 本轮不得改变后台 RBAC、生产环境变量或 CloudBase 资源。

## 6. 测试策略

严格执行 Red → Green → Refactor：

1. 先为 QA 历史 claim 新旧轮次写失败测试，覆盖正式用户、同轮 QA、跨轮 QA、字段缺失 fail-closed。
2. 为职业搜索、分组、最多两个选择写纯函数失败测试，再接入页面。
3. 为揭晓的 view/dismiss/storage failure 语义写失败测试。
4. 为 custom tabBar 的页面白名单和选中态写合同测试。
5. 扩展完整 formal matching 自检，不能只断言 `rankCandidates`。
6. 运行小程序语法、Agent、匹配 v1.8、RBAC、安全、E2E 14 场景回归。
7. UI 改动通过微信开发者工具或可用浏览器/截图路径做视觉检查；无法自动执行的真机步骤明确保留为人工验证。

## 7. 验收标准

- 同一对显式 QA 账号在完成新一轮重录后可以再次验证成功匹配，同时正式用户仍不能重复配对。
- 超过两个补充身份会被阻止；注册页不再平铺几十个职业标签。
- 三个 tab 都有一致、清晰、选中态正确的线性图标。
- “稍后再看”不会永久吞掉匹配揭晓；“立即查看”在 storage 失败时仍能进入详情。
- 后台会话入口的权限投影不被扩大。
- 所有新增测试经历可证明的 Red/Green，完整回归退出码为 0。
- 工作区无意外生成物，无部署、无 push、无生产写入。

## 8. 独立框架审查

主实现和验证完成后，按用户要求启动一个只读 subagent。它将检查：

- 小程序页面/组件边界与重复逻辑。
- Cloud Function 与 Express 双后端重复和版本漂移。
- LangGraph、确定性后端与 RAG 开关的实际执行路径。
- 测试分层、CI、部署版本可追踪性。
- 数据模型渐进字段与索引风险。

subagent 不修改文件；主 Agent 将复核其证据后，把建议分为 P0/P1/P2，并区分本轮应修与后续路线图。
