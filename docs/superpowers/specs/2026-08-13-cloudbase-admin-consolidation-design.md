# WeFinally CloudBase 管理后台整合设计

日期：2026-08-13
状态：已确认，待实施计划

## 1. 目标

将旧本地 MySQL 管理后台的完整业务能力迁移并整合到现有 CloudBase 管理后台。最终线上后台保留单一入口、单一认证体系和单一 CloudBase 数据源，不再依赖本地 MySQL。

第一批优先解决客服识别用户困难的问题：管理员在一个页面内看到用户档案、会员状态、订单、匹配记录、AI 会话、人工客服、工单和约会协调记录，并能继续人工回复。

## 2. 已确认的现状

- `server/public/admin/index.html` 仍包含 18 个管理模块，并非旧版页面丢失。
- 线上使用 `cloudOnly=1` 时，仅开放客服工作台、会员审核、合伙人管理和 AI 知识库 4 个模块。
- 其余模块调用本地 Express/MySQL 接口，因此线上被主动隐藏。
- CloudBase `agent_sessions` 当前共有 4 条会话：3 条属于真实微信用户 `1783497710464352`，1 条属于旧本地测试用户 `118`。
- 两个用户档案均没有昵称，后台不能依赖昵称识别用户。
- 测试用户 `118` 的 OpenID 为 `dev_wefinally_local_openid`，不得与真实微信用户强行合并。

## 3. 方案选择

采用“CloudBase 原生、分批完整整合”。

不采用以下方案：

- 一次性迁移全部模块：改动面过大，无法以小批次验证线上行为。
- 线上后台反向代理本地 MySQL：继续引入本地服务依赖，不满足一体化部署目标。
- 重写一套新后台：重复现有完整页面，并增加功能遗漏风险。

现有页面继续作为唯一管理前端；旧 MySQL 路由按业务域迁移到 CloudBase NoSQL 服务，迁移完成一个域后开放对应导航。

## 4. 用户识别设计

### 4.1 双 ID 模型

- `id`：保留现有内部主键，继续关联订单、匹配、会话和审核记录，禁止批量改写。
- `support_code`：新增面向管理员的稳定短编号，格式为 `WF-000001`。
- 测试账号显示为 `TEST-000118` 等测试编号，不占正式编号空间。

正式用户编号由服务端集中分配并持久化到用户文档；已分配后不可修改。分配过程必须具备并发安全和冲突检测，不允许前端自行计算。

### 4.2 展示规则

会话队列、用户列表、订单、匹配记录和工单统一展示：

`WF-000001 · 女 · 深圳`

缺失资料时显示：

`WF-000001 · 资料未完善`

原始长 ID、OpenID、手机号等敏感或技术字段仅在有权限的详情区域展示，并记录查看审计。不得生成虚假昵称。

### 4.3 测试数据隔离

满足以下任一条件的账号视为测试数据：

- `is_test_fixture = 1`
- OpenID 使用明确的开发/测试前缀，例如 `dev_`
- 已登记的 A/B 测试候选或本地迁移测试账号

正式客服队列默认排除测试数据，但提供“包含测试数据”筛选。测试数据不删除、不并入真实用户。

## 5. 第一批：用户中心与客服聚合

### 5.1 CloudBase 后端

在云函数后台服务中新增独立的用户管理服务，避免继续扩大单一的 `backoffice.js`：

- 用户列表与检索
- 用户聚合详情
- 匹配记录列表与详情
- 订单列表与用户订单摘要
- 用户客服上下文
- 用户短编号分配与测试数据判定

第一批接口：

- `GET /api/admin/dashboard`
- `GET /api/admin/users`
- `GET /api/admin/users/:id`
- `PUT /api/admin/users/:id`
- `GET /api/admin/matches`
- `GET /api/admin/matches/:id`
- `GET /api/admin/orders`
- `GET /api/admin/agent/conversations/:id`

用户聚合详情至少返回：

- 基础档案和 `support_code`
- 会员申请、VIP 状态和来源
- 合伙人归属与邀请来源
- 订单摘要
- 匹配偏好和匹配历史
- AI/人工会话与消息
- 客服工单、约会协调和通知记录
- 测试数据标识

### 5.2 管理后台

- 在 CloudBase 模式开放数据看板、用户管理、匹配记录和订单对账。
- 客服工作台右侧上下文改为完整用户摘要，不再只展示脱敏长编号。
- 点击用户编号进入同一聚合详情，不打开平行的第二套用户页面。
- 旧“客服会话”和“奔现工单”能力合并进入客服工作台的筛选/标签页；迁移完成后移除重复导航。
- 默认隐藏测试用户和测试会话，管理员可手动切换查看。

### 5.3 权限与审计

- `super_admin`：可查看和修改用户业务状态。
- `customer_service`：可查看完成客服所需的档案摘要、订单状态和会话，可回复；不可修改用户核心资料或导出数据。
- 敏感字段查看、用户修改、人工回复和工单关闭必须记录审计。
- 后端必须执行角色校验，不能只依赖前端隐藏按钮。

## 6. 后续批次

### 第二批：业务管理

- 提现审核
- 婚姻报备
- 注销及离异审核
- 公示数据配置
- 业务看板补全

### 第三批：运营与合规

- 隐私授权日志
- 单位白名单与导入批次
- 数据导出
- 系统日志
- 旧 MySQL 路由与重复导航清理

每个模块只有在 CloudBase 接口、权限和浏览器验证均通过后才对线上导航开放。

## 7. 数据流

1. 管理员通过现有后台账号登录 CloudBase 后台接口。
2. 前端只调用 CloudBase 服务域名，不回退到本地 `/api`。
3. 聚合服务以内部 `user_id` 查询现有 NoSQL 集合。
4. 服务端应用角色权限、测试数据过滤和敏感字段裁剪。
5. 前端使用 `support_code` 展示用户身份，同时保留内部 ID 进行后续请求。
6. 修改、回复、导出或敏感查看写入审计记录。

## 8. 错误处理

- 某一关联集合暂无记录时返回空数组或空摘要，不让整个用户详情失败。
- 用户主记录不存在时返回明确的 404，不展示孤立会话为正常用户。
- `support_code` 分配冲突必须重试或失败，不允许返回重复编号。
- 测试数据判定只能影响默认展示，不得删除或改变业务记录。
- 聚合接口不得把密码哈希、完整令牌或不必要的 OpenID 返回给客服角色。

## 9. 测试与交付

每个批次严格执行红—绿—重构：

1. 先新增接口契约和浏览器 fixture 测试，并确认因缺少能力而失败。
2. 实现最小 CloudBase 服务和前端改动，使新增测试通过。
3. 运行对应 selfcheck、语法检查和现有回归测试。
4. 审查本批 diff，仅提交本批文件并报告 commit hash。
5. 通过 CloudBase MCP 部署云函数与静态托管。
6. 在线验证登录、导航、用户聚合详情、测试数据筛选和人工回复。

第一批完成标准：

- 真实微信用户的 3 个会话归到同一 `WF-xxxxxx` 用户上下文。
- 旧本地用户 `118` 显示为测试账号且默认不进入正式队列。
- 无昵称用户仍可通过短编号、性别和城市稳定识别。
- 管理员在同一页面看到档案、会员、订单、匹配和客服历史。
- 客服角色只能看到并操作授权范围内的数据。
- 线上后台不依赖本地 MySQL 才能完成上述流程。

## 10. 非目标

- 不合并不同 OpenID 或不同内部用户 ID 的记录。
- 不删除历史测试数据。
- 不重做后台视觉系统。
- 不在本批部署小程序、修改生产匹配结果或处理真实资金。
