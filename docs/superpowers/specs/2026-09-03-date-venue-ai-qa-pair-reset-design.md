# WeFinally 场地 AI 澄清与双真机 QA 成对重置设计

## 背景与目标

当前第一次约会表单把“活动场地”同时当作活动类型、商圈和具体门店使用，导致“吃饭 + 大运中心”“吃椰子鸡”等合理但不完整的表达被硬校验拒绝，甚至在异常未正确投影时显示 `SERVER_ERROR`。同时，双真机 QA 会留下多轮匹配、协调和 AI 会话数据，使测试人员难以判断问题来自新代码还是旧状态。

本设计完成两个目标：

1. 允许用户先表达商圈或餐饮类型，由 AI 进行结构化澄清；最终方案仍需明确到可赴约的具体活动场地。
2. 增加只面向当前两名 QA 测试账号的“一键彻底重置双机测试”，删除匹配与约会协调衍生数据，但保留账号、注册资料、画像/RAG、会员、支付和邀请归因。

## 一、场地与活动语义模型

### 1.1 三类输入

后端将用户输入拆成三个独立概念：

- `area`：行政区或商圈，例如“龙岗区”“大运中心附近”。
- `activity_detail`：活动或餐饮类型，例如“椰子鸡”“看电影”“喝咖啡”。
- `activity_venue`：可执行的具体场所，例如“润园四季椰子鸡大运店”“深圳仁恒梦中心英皇电影城”。

“大运中心”不能被解释为某家餐厅，但可以作为 `area/venue_hint`；“椰子鸡”不能冒充门店名，但可以作为 `activity_detail`。二者都属于可继续协调的信息，而不是服务器异常。

### 1.2 状态与完成条件

约会草案新增脱敏、结构化的场地澄清状态：

```text
venue_resolution.status = resolved | needs_specific_venue
venue_resolution.area_hint
venue_resolution.activity_detail
venue_resolution.missing = [activity_venue]
```

- 初始邀请可携带 `needs_specific_venue`，并明确展示“具体门店待确认”。
- AI 可以理解自然语言并生成候选解释/追问，但不能直接把自由文本写成最终方案。
- 用户确认 AI 生成的结构化修改预览后，才更新自己的申请版本。
- 只有 `activity_venue` 明确、具体时间存在、活动与场地不冲突时，才能生成最终候选方案并进入双方确认。

### 1.3 AI 引导文案

AI 的回复应引用已确认的上下文，而不是泛化报错：

- “大运中心附近可以。你更想吃哪一类，或者有具体门店吗？”
- 用户说“椰子鸡”后：“已记为餐饮偏好。还需要确认具体门店，例如某某椰子鸡大运店；要我继续和对方协调门店吗？”
- 如果用户直接填写具体店名，则展示结构化预览，确认后更新方案。

AI 输出必须带“AI 生成内容，仅供参考”；不得推荐或推断家庭住址、单位、学校等私密地点。

### 1.4 前端交互

第一次约会表单将“活动场地”改为“想去哪里 / 吃什么”，允许填写商圈、活动类型或具体店名。输入不够具体时：

1. 不显示 `SERVER_ERROR`。
2. 表单顶部出现浅紫 AI 澄清卡，说明系统当前理解到的区域、类型和缺失项。
3. 主按钮文案变为“发送邀请并继续完善”；先保存带 `needs_specific_venue` 的初始邀请，再进入当前协调任务的 AI 会话。
4. 对方可以回应活动类型、区域和时间，但系统不得把待完善邀请误显示为可最终确认的约会方案。
5. AI 会话展示每次结构化修改预览；用户确认后保存新版本，双方均确认具体场地后才生成最终方案。

如果输入已经是具体场地，主按钮保持“发送第一次约会邀请”。

## 二、双真机 QA 成对彻底重置

### 2.1 安全边界

入口只在内部 QA 面板显示。服务端必须同时满足：

- 当前用户为 `internal_qa`，或属于已开启的双真机 QA cohort。
- 服务端根据 cohort 和现有匹配关系解析另一名 QA 用户，不能信任客户端提交的 partner user id。
- 恰好解析出两名合格的真实 QA 账号；存在歧义时拒绝执行并返回明确错误。
- 客户端提交确认文案：`彻底清空本对测试数据`。

### 2.2 删除范围

删除所有由这两名 QA 用户参与的匹配测试所派生的数据。服务端先解析两人的全部匹配记录，再以这些 match id、coordination id 和 session id 反向收集删除目标；不能仅按页面当前记录删除：

- 双方的 `user_match_log`，以及由这些匹配记录关联的匹配报告、报告任务、反馈、match claim/audit。
- 由上述匹配记录派生、且任一 QA 用户参与的 `date_coordination`，以及对应 application、proposal、confirmation、patch、event、event dedupe、fixture response job。
- 上述协调任务对应的 `date_coordinator` agent session、agent message、message dedupe、notification job。
- 上述协调任务和两名用户对应的站内协调通知及通知 dedupe；重新计算或清零两人的通知 cursor。
- 协调会话单例锁 `agent_session_dedupe`。

不删除：

- `user` 账号和 OpenID。
- 注册资料、择偶配置、身份标签、用户证据、RAG corpus/embedding、AI 匹配画像。
- VIP、订单、支付、合作人邀请与佣金归因。
- 与匹配或约会协调无关的普通 AI 恋爱助手会话。
- 合成 fixture 用户本身。

### 2.3 重置后的用户状态

两名用户恢复为可参加下一轮双真机互配：

- 清除 `matched_partner_id` 和当前匹配占用状态。
- 清除旧 QA real-device run/enrollment 的完成状态，生成新的 pair reset generation。
- 不改变会员审核状态和资料完整度。

### 2.4 可恢复执行与审计

跨集合硬删除不能假装为单一原子事务。服务端创建 `qa_pair_reset_run` 控制记录，使用稳定 request id 幂等执行：

```text
pending -> deleting -> resetting_users -> completed
                         \-> failed_retryable
```

- 每个阶段记录集合删除数量，不记录聊天正文或个人资料。
- 重复点击返回同一 reset run，失败后从未完成阶段继续。
- 只有全部删除及双方状态重置成功后，UI 才显示“已彻底重置”。
- 保留单独的脱敏 `qa_pair_reset_audit`：操作者内部 user id、pair hash、时间、删除数量、结果；审计记录不参与业务读取。

### 2.5 UI

QA 面板新增危险级次按钮“彻底重置双机测试”。点击后弹出二次确认：

> 将删除这两个测试账号的全部匹配记录、第一次约会协调和 AI 协调聊天。注册资料、画像/RAG、VIP 和订单会保留。

确认按钮为“彻底重置”，执行中显示阶段进度；完成后刷新 QA access 和匹配页。原“重新注册测试资料”保持独立，不与本操作合并。

## 三、错误处理与当前 SERVER_ERROR

本功能不能用宽松校验掩盖当前 500。场地输入的可解释不完整状态返回稳定业务码，例如 `DATE_VENUE_NEEDS_CLARIFICATION`，并附安全的结构化澄清数据；数据库或程序异常仍返回服务器错误。

当前线上失败已经确认发生在申请记录写入之前，但由于 CLS 未开启，还没有真实异常栈。实现时增加不包含表单正文的阶段错误日志（`normalize / primary_resolution / application_write / event_publish`）。启用 CLS 仍需用户单独确认；不在本次部署中自动修改日志服务或计费配置。

## 四、测试与发布验收

### 自动化

- “吃饭 + 大运中心”进入 `needs_specific_venue`，不写最终方案、不返回 500。
- “椰子鸡”保存为 `activity_detail`，AI 继续询问具体门店。
- 具体门店通过结构化预览后可进入邀请/最终方案流程。
- 模型不可绕过权限、版本、状态机或最终场地完整性检查。
- 非 QA、单账号、客户端伪造 partner id、确认文案错误均无法重置。
- 同一 reset request 并发/重试只生成一个 run；阶段失败后可恢复。
- 删除仅覆盖双方匹配及 `date_coordinator` 衍生记录；画像/RAG、VIP、支付、邀请归因和普通 AI 会话保持不变。
- 六组发布基线与 LangGraph、QA、通知并发专项全部通过。

### 部署

- 先推送明确代码 SHA，再从该 SHA 的干净归档部署现有 `api`；若 Agent Graph 合同发生变化，再按依赖顺序部署 `agent-graph`。
- 不修改运行时、环境变量、权限、触发器或日志计费配置。
- 云函数与小程序体验版分开记录；UI 变更必须另行上传体验版后才能在真机看到。
