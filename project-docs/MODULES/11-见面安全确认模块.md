# 模块 11：见面安全（110 方案一）

> 来源升级：老板原话 A7 +《微信小程序对接深圳110系统的合规解决方案.docx》。
> ⚠️ **本模块范围已扩大**：老板明确要做「方案一安全功能」，含 **LBS 定位 + 紧急联系人 + 一键呼救**——**覆盖**早期 C2/Q5「v1 不做实时定位/紧急联系人/一键报警」的决定。

## 产品定位

- 仍是**官方客服对接奔现之后**的用户自我安全层，文案：**线下见面安全确认**。
- 分两阶段（老板原话）：
  - **方案一（现在做，完全合规，不直连公安）**：见面报备 + LBS 一键呼救（跳转官方「广东110」小程序）+ 平台内部预警。1–2 周可上线，无资质门槛。
  - **方案二（用户量大后再做）**：报警信息直推深圳公安接警台。需 ICP 证、等保二级、APP/公安备案、警企合作，3–6 个月。**v1 不做，仅留演进位**。

## 方案一 MVP 范围

### 做
1. **见面报备表单**：见面对象、LBS 定位、见面时间、见面说明、**紧急联系人**（亲友手机号）。数据留存于自有服务器作证据链；字段级加密列为上线前安全项，不在 MVP 中伪装完成。
2. 安全提示勾选「我已阅读线下见面安全提示」。
3. 报备状态（见面前/进行中/结束）；用户主动开启“安全守护”后，页面前台运行时通过 `wx.startLocationUpdate` + `wx.onLocationChange` 上传定位轨迹；用户可手动结束守护。
4. 历史记录列表。
5. **一键呼救（已定型 v1）**：
   - ① **跳转「广东110」官方小程序**：AppID 已配置为 `wxf654be7f2931bfcb`；官方 path 未拿到前只打开首页。开发者工具只显示“跳转成功”的校验页，真实跳转需真机测试。
   - ② **跳转失败兜底**：展示微信底层 `errMsg`，并引导用户复制/搜索「广东110」官方小程序；不把“拨打110”作为默认实现。
   - ③ **平台内部预警**：呼救即写一条 SOS 记录(定位/紧急联系人/时间，证据链)。首页 SOS 无报备也写 `meet_report_id=0`。⚠️ **暂无短信服务商、暂无 24h 客服人力** → v1 先记录 + 引导用户自行联系紧急联系人；真实短信/推送/客服值守后接。
6. ~~见面安全卡（脱敏）+ 用户主动转发给本人好友/家人~~ → **已撤下(2026-06-29)**。安全卡是 C3(John 新增)、不在老板 110 文档里；老板明确「按照我的提示来，不要自己来」→ v1 不做，严格只对齐老板 110 方案一。安全卡降级为**待老板确认**项，他点头再加。（前端已移除卡片展示+转发；后端 `card_no` 字段保留无害）

### 不做（合规红线 + v1 范围）
- **不直连/不宣称"直连110出警系统"**（只能写「跳转广东公安官方报警小程序，同步实时定位」，虚假宣传会被处罚）。
- LBS **必须用户主动授权**，仅见面报备/呼救场景用，**禁止后台静默持续采集**。
- 用户端上传照片、复杂风控模型、默认展示手机/身份证/真实姓名。
- 安全卡不在小程序内发给匹配对象、不公开展示、v1 不做存相册（沿用 Q5）。
- 见面报备 ≠ 平台免责（仍需实名/黑名单/杀猪盘风控）。
