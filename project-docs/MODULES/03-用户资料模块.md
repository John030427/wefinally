## 需求（2026-06-29 已确认 · v1 范围）

| 规则 | 结论 |
|------|------|
| 字段名 | `appearance_description` |
| 内容 | 用户**自填纯文本**，描述长相、体型、穿搭、发型、气质等 |
| 禁止 | 上传真实照片、颜值打分、歧视标签 |
| 填写 | **选填**，强引导但不强制、不阻断其他功能 |
| **可见性（v1）** | **默认不展示给匹配对象**；仅本人可见 + **后台可见**（辅助风控/对接） |
| **是否进入 v1 匹配打分** | **否**（`useAppearanceInMatch = false`）；v1 是结构化权重 + 三观 Jaccard，无法可靠解析自由文本外貌 |
| UI | **在已有 profile 页增加**，不新建页面 |

> 决策来源：Q4 / B-Q2（2026-06-29 John 拍板）。相较初版设计的「匹配成功后展示给对方」，v1 **收紧为不展示**，更隐私保守。

## v2 LLM 画像（已立项 · 未排期）

> 来源：John 2026-06-29 提出。**这是 v2 增强，不在 v1 范围**，且会触碰「v1 不接外部大模型」的已确认决定。

**设想**：用户只打几个关键词（如「高、瘦、文艺、戴眼镜」），由大模型结合其它资料**生成一段通顺的用户画像文本**（大模型在此是「写手」，不是匹配判官）。

**与「LLM 匹配（路线 B）」的区别**：路线 B 是把两人资料喂给大模型做兼容性判断/生成匹配理由（「判官」）。本功能只生成单人画像文案（「写手」），二者独立。

**落地前必须先确认（已登记入 QUESTIONS_TO_BOSS 衍生需求）**：
1. 用哪个大模型 / 服务商、按量成本是否接受
2. 生成的画像给谁看（本人确认？后台？是否展示给对方——若展示则与 Q4 冲突需重审）
3. **内容安全机审方案**（生成"长相/身材"文本有冒犯风险，婚恋类目审核敏感——最大风险点）
4. 个人信息授权文案（PII 发外部模型，个人信息保护法）
5. 是否改「v1 不接外部大模型」这条决定（可能需老板点头）

**生成延迟**：1–3 秒，注册/编辑交互需异步 + loading。
