# Agent 工作规则

> 本文档约束所有参与 WeFinally 婚恋小程序开发的 Agent（含主模型与 sub-agent）。
> 最后更新：2026-06-29

---

## 一、最高优先级原则

凡用户明确写成「老板说」「老板要求」「老板强调」的内容，均为本项目**最高优先级需求**。

老板已明确说过：

1. **继续基于已有项目开发** — 不是从零开发，不重写项目
2. **对已写好的代码进行 review 和重构** — 系统性审计，小步重构
3. **用已经做好的 UI** — 复用现有页面、组件、样式
4. **不要推翻已有 UI 重新做一套**
5. **新功能尽量接入已有页面、组件和样式**
6. **老板的产品想法要持续贯彻** — 不能只在第一轮理解后就丢掉

### 需求来源优先级

| 优先级 | 来源 | 处理方式 |
|--------|------|----------|
| 1（最高） | 老板明确说过的话 + PRD 文档 | 必须执行 |
| 2 | 用户（John）新增的产品需求 | 纳入当前总需求 |
| 3（参考） | 豆包、早期聊天、客服聊天、历史想法 | 仅作背景，**不能高于老板明确说过的话** |

**不确定是否为老板原意时**：不得擅自当成老板需求，必须写入 `QUESTIONS_TO_BOSS.md` 待确认。

## 二、已确认的核心产品决策（2026-06-29）

以下已由用户确认，后续开发必须遵守：

| 决策项 | 确认结论 |
|--------|----------|
| 商业模式 | 以 PRD 为准：严肃婚恋 + 188元/30天 + 官方客服对接奔现 |
| 离婚证明 | 支持图片或 PDF，走管理员/客服后台人工审核（用户端无上传入口） |
| 线下见面安全确认 | 官方对接奔现**之后**的用户自我安全确认附加层，不是自助发起见面 |
| 配置化方案 | 后端 `server/src/config/*` 为真源 + `GET /api/common/config` 下发前端 |
| 算法第一版 | 三观字符相似度 + AI 客服关键词匹配够用，v1 不接外部大模型 |
| 匹配池 | 被匹配对象**不要求**必须是付费 VIP |
| 双向互配 | **必须做** — 双向契合 + 对称记录，保护用户体验和安全感 |

## 三、开发行为准则

### 3.1 修改前

1. 说明本次修改的**目的**和**范围**
2. 确认是否影响已有 UI（如影响，必须先说明）
3. 不确定是否该改的地方，先问用户/写入 `QUESTIONS_TO_BOSS.md`
4. 每次只做**小范围**修改，不做未经确认的大规模重构

### 3.2 修改后

1. 更新 `DEVELOPMENT_LOG.md`（记录变更内容、原因、涉及文件）
2. 更新 `DEVELOPMENT_PROGRESS.md`（当前阶段、已完成、下一步）
3. 重要设计决策写入 `README_HANDOVER.md` 或对应 `MODULES/` 文档

### 3.3 禁止事项

- 不随意删除原代码
- 不做未经确认的大规模重构
- 不推翻老板已有 UI
- 不把可变参数写死在页面/业务逻辑中（见 `CONFIG_DESIGN.md`）
- 不编造老板没说过的需求
- 不让 sub-agent 自行决定重大架构调整

## 四、UI 复用规则

后续开发必须遵守：

1. 有个人资料页 → 在已有 `profile` 页加入新字段（如外貌描述）
2. 有匹配页 → 在已有 `match-detail` / `index` 接入新逻辑
3. 有聊天/约见入口 → 在已有 `match-detail` 的奔现卡接入线下见面安全确认
4. 有卡片组件 → 用已有 `.card` 样式做见面安全卡
5. 有列表样式 → 用已有 `match-list` 样式展示报备记录
6. **不要为了新增功能重新做一整套 UI**

全局设计系统位于 `miniprogram/app.wxss`，详见 `UI_REVIEW.md`。

## 五、配置化规则

凡是后期可能调整的内容，必须放到统一配置位置，不散落在页面文件中。

- 后端真源：`server/src/config/`（`constants.js`、`productConfig.js`、`matchConfig.js`、`safetyConfig.js` 等）
- 前端镜像：`miniprogram/utils/constants.js` + 启动时从 `GET /api/common/config` 拉取
- 详见 `CONFIG_DESIGN.md`

新增功能前，先判断该参数是否应加入配置文件。

## 六、Sub-agent 使用规则

允许使用 sub-agent 协助，但必须受控：

| 允许 | 不允许 |
|------|--------|
| 代码扫描、UI 审计、文档整理、测试检查、AI 匹配研究 | 自行决定重大架构调整 |
| 提出小步重构方案（主模型审后执行） | 未经主模型确认直接大规模改代码 |

**主模型职责**：最终判断、开发计划、风险说明、汇总 sub-agent 结论。

**记录要求**：每个 sub-agent 的任务和结论写入 `DEVELOPMENT_LOG.md`；结论冲突必须列出。

建议分工：

| Agent | 用途 |
|-------|------|
| Code Review Agent | 审计已有代码 |
| UI Review Agent | 审计已有 UI |
| Product Requirement Agent | 拆解需求（老板原意判断由主模型完成） |
| AI Matching Research Agent | 研究 AI 匹配方案 |
| Refactor Agent | 提出小步重构方案 |
| Test Agent | 检查运行、预览和报错 |

## 七、重构原则

1. 重构不是重写
2. 不要推翻老板已有代码和 UI
3. 优先保证项目能运行
4. 每次只做小范围重构
5. 重构前说明计划，重构后更新日志

第一轮重构顺序（详见 `TODO.md`）：

- R0：跑通项目（不改码）
- R1：修确定性 Bug（不影响 UI）
- R2：配置化收敛（无行为变更）
- R3：安全加固（不影响 UI）
- R4+：匹配逻辑修正（双向互配、候选放开非 VIP）— 需专项测试
