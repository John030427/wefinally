# 匹配算法多场景离线夹具（2026-07-26）

## 目的与边界

这组夹具用于离线验证确定性硬筛、双向评分和质量门槛，不创建云端用户，
不包含手机号、OpenID、精确地址、单位或其他可识别信息，也不执行数据库写入。

夹具实现：

```text
server/selfcheck/fixtures/match-scenarios.js
```

验证入口：

```powershell
node server/selfcheck/match-scenario-fixtures.js
```

## 固定场景与当前算法基线

| 场景 | A 原始分/百分比 | B 原始分/百分比 | 双向门槛 | 预期原因 |
| --- | ---: | ---: | --- | --- |
| `high_fit` | 123.77 / 97% | 127.10 / 99% | 通过 | 高契合但不全满 |
| `medium_fit` | 104.52 / 82% | 104.52 / 82% | 通过 | 圈层、城市、关系偏好等存在差异 |
| `edge_pass` | 90 / 70% | 90 / 70% | 刚好通过 | 双方原始分等于 `minSideScore=90` |
| `hard_reject` | 不评分 | 不评分 | 硬筛淘汰 | 候选年龄不在 A 的硬条件区间 |
| `missing_data` | 55 / 43% | 55 / 43% | 不通过 | `side_score`；关系偏好与外貌证据缺失 |

这些数值是当前 `algo_evidence_v2` 的回归基线。权重或质量门槛变更时，必须显式
更新场景预期并说明原因，不能为了让测试通过而放宽范围。

## 后续接入规则

1. 先把这组夹具用于纯算法排序 A 组与 Agent 重排 B 组的离线评估。
2. Agent 只能接收硬筛后的脱敏 Top-K 特征，不能读取全库。
3. Agent 输出只能是候选相对顺序、证据、风险和置信度，不能直接写数据库。
4. 最终硬条件、黑名单、重复匹配和质量门槛仍由确定性后端执行。
5. 如需将场景接入后台“准备 A/B 测试”，必须继续沿用超级管理员权限、
   owner/run/fixture 三重标记、幂等 request ID 和审计清理流程。
