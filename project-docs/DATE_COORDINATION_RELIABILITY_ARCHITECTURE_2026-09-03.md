# 约会协调可靠性架构（2026-09-03）

## 目标

让双真机约会协调在重复点击、弱网重试、云函数并发和旧会话并存时，仍满足以下不变量：

1. 一次业务事件只保存一条事件事实。
2. 同一协调任务中，每位参与者只有一个未关闭的 AI 协调会话。
3. 每个参与者对同一事件只收到一条脱敏投影消息。
4. 通知记录与未读计数同步提交；用户正在标记已读时，新到通知不能丢失。
5. LangGraph 负责理解、澄清和反馈；权限、版本、幂等、状态迁移及正式写入由确定性后端负责。

## 当前写入链路

```text
用户输入 / 表单确认
  -> API 权限与 coordination_version 校验
  -> 确定性业务提交（事务/CAS）
  -> date_coordination_event（稳定幂等键）
  -> 每位参与者的 agent_session（稳定单例锁）
  -> agent_message（事件 × 用户幂等投影）
  -> coordination_notification + user_notification_cursor（同一事务）
```

协调事件、会话和消息只保存安全投影，不复制对方原始回答、联系方式或私密上下文。旧会话不删除；读取时选择最新未关闭会话，新事件不会再创建第二个活跃会话。

## 本轮完成的可靠性边界

- `agent_session_dedupe` 以“用户 + Agent 类型 + 协调任务”为稳定键，在事务内复用或创建会话；首次上线会优先接管已有未关闭会话，不强制迁移历史记录。
- 通知已读由 `markCoordinationNotificationsSeen` 在单个 CloudBase 事务内更新通知行和未读游标。
- 小程序提交 `through_notification_id` 水位，只标记用户实际加载到的通知；水位之后的新通知保持未读。
- 修正公共错误返回结构：`code` 保持 HTTP 数字状态，`error` 才承载稳定业务错误码。
- 并发自检必须打印最终 PASS；未抵达末尾的悬空 Promise 不再被当作测试成功。

## 下一阶段（不阻塞本次发布）

### P1：事务 Outbox

目前站内通知事实已可靠，但微信订阅消息仍在事务提交后调用。后续应新增 outbox/job：事务只写待发送任务，worker 负责重试并记录 `pending/sent/skipped/failed`，避免进程在提交后退出造成外部通知漏发。

### P1：真实 CloudBase 并发验证

现有测试用内存串行器验证契约；还需要在隔离 QA 数据上验证 CloudBase 事务冲突重试、集合首次自动创建以及双手机未读水位。不得使用正式用户数据。

### P2：可观测性

按 `coordination_id + coordination_version + event_key` 输出脱敏 trace，统计重复命中、投影补偿、事务重试和 outbox 延迟；日志不得包含对方原话、手机号、OpenID 或精确现场描述。

### P2：历史会话整理

为既有重复活跃会话提供一次只读审计和受控修复工具：保留最新会话为 active，其余标记 closed。该动作必须单独审批、先 dry-run，不能随云函数部署自动修改生产数据。
