# 合伙人名单制免密激活与审核需求

## 1. 问题与目标

当前合伙人需要独立的手机号和密码登录，小程序“我的”页面又只在本地已经存在合伙人 Token 时展示入口，导致已被认可的合伙人无法发现或顺畅进入工作台。平台需要把老板认可的手机号名单、管理后台审核、小程序微信身份和现有邀请/收入能力连接成一套可审计的流程。

目标是让合伙人首次完成手机号持有验证并绑定当前微信，之后免密码进入分享与收入 Dashboard；普通用户不能因为知道一个手机号或填写普通邀请码而获得合伙人权限。

## 2. 角色与用户故事

### 2.1 普通用户

- 作为普通用户，我希望在“我的”页面看到合伙人计划入口，并能理解当前资格状态。
- 作为被合伙人邀请的用户，我希望邀请码只用于注册归因和会员审核，不改变我的账号角色。

### 2.2 名单合伙人

- 作为老板认可且已录入手机号名单的合伙人，我希望首次在小程序验证本机手机号后激活身份，不需要设置或记忆密码。
- 作为已绑定合伙人，我希望以后点击“我的 → 合伙人工作台”即可进入。
- 作为合伙人，我希望看到自己的邀请码、分享素材、邀请转化和收入数据。

### 2.3 申请人

- 作为不在预批准名单中的用户，我希望可以提交合伙人申请并查看审核状态。
- 作为被驳回的申请人，我希望看到可公开的驳回原因并可以补充后再次申请。

### 2.4 管理员

- 作为管理员，我希望录入或导入老板认可的手机号名单，并审批普通用户提交的合伙人申请。
- 作为管理员，我希望批准、驳回、暂停、恢复、解绑微信或撤销合伙人权限，且所有操作可审计。

## 3. 核心业务规则

1. 普通用户邀请码与合伙人资格严格分离。普通邀请码只能产生邀请归因，不能授予后台权限。
2. 合伙人资格来源有两种：管理员预批准名单，或用户申请后由管理员批准。
3. 仅输入一个与名单匹配的手机号不足以完成登录；首次激活必须验证手机号持有权，并绑定当前小程序微信身份。
4. 首次绑定后，以可信微信身份识别合伙人，后续免密码进入；换微信或解绑必须经过管理员操作或重新验证。
5. 一个有效合伙人默认只能绑定一个小程序用户身份；同一手机号和同一用户不能重复激活多个合伙人。
6. 合伙人编号采用稳定、可识别且与用户编号区分的格式 `WF-P-0001`；数据库关系仍使用不可变的内部 `partner_id`。
7. 对外邀请码采用稳定格式 `WFP0001`。旧邀请码必须继续有效，历史归因不得因新编号上线而丢失。
8. 分享链接和小程序码优先携带签名归因参数；手动邀请码作为兼容和线下输入方式。
9. 合伙人只能查看属于自己的汇总、邀请与佣金数据，不能读取其他合伙人的数据或不必要的用户隐私。
10. 暂停或撤销权限后，新会话必须立即拒绝进入合伙人工作台；历史财务和审计记录必须保留。

## 4. 用户流程与状态

### 4.1 “我的”页面

“我的”页面应始终展示“合伙人计划”入口，并根据服务端状态显示：

- `not_applied`：申请成为合伙人
- `pending`：申请审核中
- `needs_verification`：已获资格，验证手机号并激活
- `active`：进入合伙人工作台
- `rejected`：查看原因并重新申请
- `suspended`：权限已暂停，请联系平台

页面不得再以本地是否存在 `PARTNER_TOKEN` 作为唯一展示条件。

### 4.2 名单合伙人首次激活

1. 用户进入“合伙人计划”。
2. 输入老板名单中的手机号。
3. 点击“验证手机号并进入”，通过微信手机号授权或等效的一次性验证码证明手机号持有权。
4. 服务端比较验证后的手机号、预批准名单状态和当前微信用户身份。
5. 校验通过后完成一次性绑定并签发合伙人会话。
6. 用户进入合伙人工作台，后续无需密码。

### 4.3 申请与后台审核

1. 不在名单中的用户提交所在城市、联系方式、擅长圈层和申请理由。
2. 管理后台“合伙人审核”展示待审申请及必要用户上下文。
3. 管理员批准后生成或激活合伙人身份；驳回时必须填写对用户可见的原因。
4. 已批准但未绑定微信的记录进入 `needs_verification`；手机号验证成功后进入 `active`。

### 4.4 合伙人工作台

工作台至少展示：

- 合伙人编号和公开邀请码
- 分享给微信好友、复制邀请码、生成小程序码
- 邀请注册人数、资料待完善人数、已审核人数、VIP 转化人数
- 累计佣金、待结算佣金、可提现余额和最近收入明细
- 需要合伙人处理的会员审核入口

金额口径必须来自现有订单、佣金台账和结算状态，不允许前端自行推算不同口径。

## 5. 管理后台范围

管理后台新增“合伙人审核”工作区，并与现有“合伙人管理”整合：

- 名单单条录入与批量导入
- 待审、待验证、已激活、已暂停、已驳回筛选
- 查看申请详情、用户编号、手机号脱敏值、来源和审核历史
- 批准、驳回、暂停、恢复、解除微信绑定、撤销资格
- 显示 `WF-P-xxxx`、公开邀请码、绑定状态和收入摘要
- 所有读取敏感详情和权限变更写入审计日志

## 6. 验收标准（EARS）

### R1：入口与状态

- 当已登录用户打开“我的”页面时，系统应从服务端获取合伙人资格状态并展示对应的“合伙人计划”入口。
- 当本地不存在合伙人 Token 但服务端状态为 `active` 时，系统应恢复或重新签发可信会话，而不是隐藏入口。

### R2：名单与审核

- 当管理员录入一个合法且未重复的手机号时，系统应创建 `needs_verification` 的预批准合伙人记录。
- 当管理员批准用户申请时，系统应记录管理员、时间、原状态、新状态和原因。
- 当管理员驳回、暂停、恢复、解绑或撤销时，系统应保留完整审计日志。

### R3：免密但不裸奔

- 当未绑定用户仅提交名单手机号但没有完成手机号持有验证时，系统应拒绝签发合伙人会话。
- 当手机号验证结果与预批准名单一致且当前微信用户未与其他合伙人冲突时，系统应原子地绑定用户并激活合伙人会话。
- 当已绑定且状态正常的合伙人再次进入时，系统应根据可信微信身份免密码进入工作台。
- 当另一微信用户尝试使用已绑定手机号激活时，系统应拒绝并提示联系管理员。

### R4：编号和归因

- 当新合伙人获批时，系统应分配唯一且不可重复的 `WF-P-xxxx` 合伙人编号和公开邀请码。
- 当新用户通过有效合伙人分享链接、二维码或邀请码注册时，系统应把归因写入该合伙人的内部 `partner_id`。
- 当旧邀请码被使用时，系统应继续解析到原合伙人并保持历史归因兼容。

### R5：Dashboard 与数据隔离

- 当合伙人打开工作台时，系统应仅返回其自身的邀请、订单、佣金、结算和提现数据。
- 当合伙人查看收入时，累计、待结算和可提现金额应与后台佣金台账口径一致。
- 当一个合伙人请求其他合伙人的资源时，系统应返回无权访问且不得泄露对方数据。

### R6：权限失效

- 当管理员暂停或撤销合伙人时，系统应拒绝该合伙人的后续受保护请求。
- 当管理员解除微信绑定时，系统应使原绑定微信无法继续进入，并保留历史业务和财务记录。

## 7. 上线与兼容要求

- 现有手机号加密码登录在迁移期保留为管理员可控的兼容入口，但不再作为小程序主流程。
- 现有合伙人、旧邀请码、邀请归因、佣金和提现数据不得删除或重算。
- `TEST-000118` 与 `WF-000015` 的直接授权属于上线数据操作，必须在功能验证完成后单独确认并通过 CloudBase MCP 执行。
- 本规格阶段不上传小程序、不部署生产函数、不修改生产数据。

## 8. 非目标

- 不允许只凭手工输入手机号直接获得合伙人会话。
- 不把普通用户邀请码改造成合伙人招募码。
- 不在本阶段实现银行卡、税务或自动打款能力。
- 不向合伙人开放全量用户列表或其他合伙人的经营数据。
