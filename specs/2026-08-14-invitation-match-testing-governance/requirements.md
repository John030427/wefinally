# 邀请、定时匹配与测试画像治理需求

## 1. 目标

本规格解决四个互相关联的问题：明确合伙人公开邀请码的语义；补齐 CloudBase 周三/周五正式匹配调度；为内部测试账号提供 10 秒倒计时匹配入口；把真人资料与合成测试画像在数据库、后台、匹配和约会流程中严格隔离。

## 2. 已确认的产品决策

1. 合伙人公开邀请码是可重复使用的归因码，可发给多人，不因首次使用而失效。
2. 保留“一键分享”和“复制邀请码”，文案明确“可多人使用”。
3. 注册页填写公开邀请码只建立邀请归因并进入现有会员注册/审核流程，绝不授予合伙人角色。
4. 合伙人身份仍由后台认可名单、手机号核验和后台审核授予。若未来需要邀请新合伙人，必须另建一次性、指定手机号、可撤销的激活凭证，不能复用公开推广码。
5. 当前用户不是 Grace。运行时代码不得把 Grace 作为当前用户或合伙人的默认姓名；真实展示名只能来自已核验的当前用户/合伙人记录。生产资料改名必须等待用户提供正确姓名并单独授权。
6. 正式用户的正式匹配仍遵守“一生只成功匹配一次”。内部测试运行必须隔离，不能消耗正式 match claim。
7. 合成测试画像不能向普通生产用户开放，只能被绑定的内部测试账号用于匹配效果验证。
8. 真人与真人之间的约会意愿不得由 AI 自动拒绝。只有内部测试账号对其专属合成画像表达约会意愿时，系统才创建延迟 2—6 小时的测试拒绝任务。

## 3. 角色与术语

- 正式真人用户：真实用户资料，`profile_origin=real_user`，不一定是内部测试账号。
- 内部测试账号：真人操作的 QA 账号，`account_mode=internal_qa`，可运行隔离测试。
- 合成测试画像：系统生成的匹配案例，`profile_origin=synthetic_fixture`，不可约会、不可进入正式候选池。
- 公开邀请码：合伙人的可重复推广/归因码。
- 合伙人激活：后台名单手机号与当前微信身份绑定的受控流程，与公开邀请码无关。
- 正式批次：周三、周五面向正式用户运行的幂等匹配批次。
- 测试运行：内部测试账号触发的隔离匹配，不写正式 claim。

## 4. 用户故事与验收标准

### R1 公开邀请码可多人使用

作为合伙人，我希望同一个公开邀请码可以复制给多个好友，以便所有成功注册者分别归因到我名下。

- 当多个不同新用户使用同一启用中的公开邀请码注册时，系统应分别创建去重归因记录，并保持邀请码可继续使用。
- 当同一用户重复提交相同或不同公开邀请码时，系统应保持首次有效归因，不覆盖、不重复计数。
- 当邀请码无效或已停用时，系统应拒绝该邀请码，不得静默绑定错误合伙人。
- 当用户填写公开邀请码完成注册时，系统应保持其为普通会员角色，不得创建 partner、partner session 或合伙人权限。
- 当合伙人打开工作台时，界面应显示“一键分享给微信好友”和“复制公开邀请码（可多人使用）”。

### R2 当前身份不硬编码为 Grace

作为当前用户，我希望页面显示我的真实资料，而不是 Grace。

- 当当前合伙人记录存在已核验姓名时，系统应显示该姓名。
- 当姓名缺失时，系统应显示中性占位“合伙人”，不得显示 Grace 或其他测试姓名。
- 当后台测试夹具使用 Grace 作为虚构数据时，测试数据应明确标记为 fixture，不得污染生产当前用户展示。
- 当需要修改生产姓名时，系统实施者应在得到正确姓名和生产写入确认前停止，不得猜测。

### R3 周三/周五正式匹配可观测且幂等

作为运营人员，我希望周三、周五的正式匹配在 CloudBase 中可靠运行，并能知道有结果、无候选还是失败。

- 当亚洲上海时区到达周三或周五的配置时间时，CloudBase 匹配 worker 应尝试创建当天唯一正式批次。
- 当同一批次被定时器重复触发或重试时，系统应通过唯一 `batch_key` 保证业务只执行一次。
- 当批次没有合格候选时，系统应记录 `completed_no_match`，而不是没有记录或伪装成功。
- 当批次产生匹配时，系统应记录匹配数量、开始/完成时间和脱敏统计。
- 当批次失败时，系统应记录错误分类、可重试状态和 request ID，不得记录手机号、OpenID、自由文本或模型原始隐私输入。
- 当仓库没有 CloudBase 正式匹配 timer worker 或部署触发器时，实施者应先报告证据，不能把本地 Node cron 当作云端已运行。

### R4 内部测试按钮 10 秒模拟

作为内部测试人员，我希望点击测试按钮后在 10 秒内走完整匹配状态，以验证有结果和无结果两种体验。

- 当非内部测试账号访问首页时，系统不得渲染测试入口，后端也应拒绝直接调用。
- 当内部测试账号点击“10 秒测试匹配”时，界面应显示不可重复点击的 10 秒倒计时。
- 当倒计时结束时，客户端应以幂等 request ID 触发一次隔离测试运行，不得修改设备时间或正式批次时间。
- 当匹配成功时，界面应持久显示成功状态并允许进入测试匹配详情。
- 当没有合格候选时，界面应持久显示“本轮无匹配结果”及可解释原因摘要。
- 当资格、资料或配置不满足时，界面应显示 `blocked` 状态和可行动提示。
- 当网络或后端失败时，界面应显示 `failed` 状态并允许安全重试；重试不得重复创建结果。
- 当页面退出后重新进入时，系统应从后端恢复未完成或最近一次测试运行状态。
- 测试运行不得写正式 `match_claim`，不得消耗真人正式匹配资格。

### R5 测试画像明确标记并隔离

作为后台人员，我希望清楚区分真人资料、内部测试账号和合成画像，避免误运营或误约会。

- 当后台列出用户时，系统应显示“真人用户”“内部测试账号”或“合成测试画像”徽标，并支持筛选。
- 当普通列表未显式请求测试数据时，系统应默认排除合成测试画像。
- 当合成画像写入数据库时，系统应包含来源、测试范围、所属测试账号、运行 ID、过期时间和 `allow_date_coordination=false`。
- 当正式真人匹配运行时，系统应排除所有合成测试画像。
- 当内部测试账号运行测试匹配时，系统应只能看到归属于自己的、未过期的合成画像。
- 当合成画像过期时，系统应不再把它作为候选；清理或删除属于后续受控运维，不在运行时自动破坏数据。
- 当现有测试库需要补标时，实施者应先输出 dry-run 数量和文档 ID，再经用户确认后使用 CloudBase MCP 写入。

### R6 合成画像的延迟拒绝

作为内部测试人员，我希望测试从表达约会意愿到收到拒绝反馈的完整链路，同时不会误导或影响真人。

- 当正式真人向正式真人表达约会意愿时，系统不得创建自动拒绝任务。
- 当内部测试账号向其专属合成画像表达约会意愿时，系统应创建一条幂等测试响应任务。
- 当任务创建时，系统应使用 interaction ID 派生 2—6 小时的确定性伪随机延迟，使重试得到同一时间。
- 当延迟到期时，worker 应写入明确标记为系统测试生成的礼貌拒绝事件，并关闭该测试约会流程。
- 当请求对象为合成画像时，系统应始终禁止真实线下协调、手机号交换、客服误派单和正式通知。
- 当同一 interaction 重复请求时，系统应返回原任务，不得创建多个拒绝。
- 当测试任务失败时，后台应可见失败状态；不得回退为真人约会流程。

## 5. 非目标

- 不把公开邀请码改成一次性码。
- 不允许公开邀请码直接注册为合伙人。
- 不开放普通用户申请合伙人。
- 不修改设备或服务器系统时间来模拟匹配。
- 不让 AI 直接写数据库或自由决定延迟时间、对象身份和权限。
- 不让合成画像进入普通生产用户候选池。
- 不部署生产云函数、不上传小程序、不批量修改生产数据，除非用户另行明确授权。

## 6. 待外部确认项

以下内容不阻塞本地编码，但阻塞生产数据变更或发布：

1. 当前用户应显示的正确姓名。
2. 哪些真实用户 ID 被授权为 `internal_qa`。
3. 测试拒绝延迟最终范围是否采用 2—6 小时。
4. CloudBase timer 的时区与 cron 语义需在实施时查官方文档并通过测试确认。
5. 生产部署、生产数据补标与小程序上传均需单独确认。
